# Feature Specification: Payload admin UX for content self-serve

**Feature Branch**: `feat/011-payload-admin-ux`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "Payload admin UX for content self-serve. Make the Payload admin panel usable by a non-engineer marketing lead without a developer sitting next to them."

## Context

The content model shipped across specs 003 and 010 is sound: two content primitives (a block-composed Page and a rich-text Post), 45 layout blocks, drafts with versioning, live preview, and a committed generic seeder. What was never designed is the **admin presentation layer** — the screens a content editor actually works in. Every admin affordance today is whatever the CMS generates by default from the field definitions.

An audit of the running admin panel on 2026-08-21 (config review plus captured screenshots of the dashboard, list views, create forms, block picker, and globals) found three classes of problem:

1. **Controls that do nothing.** Several fields, one global, and two collections are fully editable but have no effect on any rendered page. An editor who fills them in and publishes sees no change and has no way to understand why.
2. **A block picker that cannot be used to pick blocks.** All 45 blocks render with an identical generic placeholder thumbnail and no description. Four are named some variant of "Hero" and are visually indistinguishable.
3. **No guidance anywhere.** 8 of 220 block fields carry help text. No collection or global has a description or grouping. Auto-generated labels expose raw field names ("Cta", "Seo", "Og Image").

The consequence is that content changes remain a developer task, which makes content the project's throughput bottleneck. This feature closes that gap. It is an **admin-only** change: no public route, template, or rendered output changes.

Canonical references: `docs/ARCHITECTURE.md` §2 (globals), `docs/BLOCK_LIBRARY.md` §5 (block categories), `docs/decisions/0009-block-first-composition.md` (two-primitive model and the expand/contract migration this feature completes), `CLAUDE.md` "Content loading & deploys" (the seeder contract that must keep working).

## Clarifications

### Session 2026-08-21

- Q: What artifact form should block previews take (FR-010, FR-013)? → A: Committed WebP screenshots in `public/block-previews/`, regenerated by a committed script
- Q: How are the human-trial success criteria SC-001 and SC-003 verified? → A: Demoted to non-blocking targets; release gates on the mechanical criteria only
- Q: What happens when a derived or entered slug collides with an existing record? → A: Reject the save, naming the conflicting record and suggesting a free slug
- Q: Do image previews need a dedicated admin thumbnail derivative? → A: No — `adminThumbnail` resolves to the smallest existing derivative; no new size, no backfill
- Q: Which Site Settings values must survive the global's withdrawal? → A: All seven consumed values move into the code-owned site-content constants; the global is withdrawn entirely

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Every editable control affects the site (Priority: P1)

A marketing editor opens any record or global in the admin. Every field they can type into, upload to, or select changes something a visitor will see. Nothing they fill in is silently discarded.

**Why this priority**: This is the trust foundation. An editor who discovers that the prominent "Hero" section at the top of the Page form does nothing, or that changing the phone number in Site Settings doesn't change the footer, stops trusting the whole panel and escalates every change back to a developer. Every other improvement in this spec is wasted while the admin is still lying.

**Independent Test**: Enumerate every editable field reachable in the admin, trace each to a consumer in the render path, and assert the set of fields with zero consumers is empty. Separately, confirm the public site renders identically before and after.

**Acceptance Scenarios**:

1. **Given** an editor creating a new Page, **When** they view the form, **Then** the form contains no section whose values are discarded at render time (specifically: the legacy `hero` group is gone, and the body is composed entirely through the block layout field).
2. **Given** an editor looking for where to change the site navigation or the footer phone number, **When** they browse the admin, **Then** they do not find an editable Navigation or Site Settings screen presenting itself as the source of truth for content that is in fact code-owned.
3. **Given** the decision that site chrome stays code-owned, **When** Site Settings is withdrawn from the admin, **Then** every value it currently feeds the render path still resolves correctly on every public route — the tagline description fallback, the social-share site name, and the company name, tagline, email, phone, postal address and social profiles emitted in the `Organization` JSON-LD.
4. **Given** an editor browsing the collection list, **When** they encounter Services and Service Pillars, **Then** they are not presented with a full page-composition body for a record type that has no public page.
5. **Given** the expand/contract migration begun in spec 010, **When** this feature ships, **Then** the retained legacy body columns are dropped and no hidden, read-only remnant fields remain in the schema.

---

### User Story 2 - Pick the right block without guessing (Priority: P1)

An editor composing a page opens the block picker, scans grouped and visually distinct options, and adds the block they meant to add on the first try.

**Why this priority**: Composing a layout is the primary act of self-serve content work under the two-primitive model. The picker is the gateway to it, and today it presents 45 visually identical cards. This is the single screen most responsible for "I don't know how to use this."

**Independent Test**: Verify in the rendered picker that every block shows a distinct preview, a category, and a description, and that the four hero-named blocks are disambiguated in their descriptions. First-try selection accuracy is the intent behind this story (SC-003) but is a target rather than a measured gate.

**Acceptance Scenarios**:

1. **Given** an editor opening the block picker, **When** the drawer renders, **Then** blocks are organized into named categories rather than one flat list of 45.
2. **Given** an editor scanning the picker, **When** they look at any block card, **Then** it shows a preview representative of what that block actually renders, not a shared placeholder.
3. **Given** the four blocks whose names all contain "hero", **When** an editor compares them, **Then** each carries a description stating what it is for and when to use it instead of the others.
4. **Given** an editor inserting a block inside rich text, **When** the inline block menu opens, **Then** each option is distinguishable there as well.
5. **Given** a new block is added to the library later, **When** it ships without a category or preview, **Then** an automated check fails.

---

### User Story 3 - Lists answer "what's live?" and "which image is this?" (Priority: P2)

An editor scanning a content list can tell at a glance which records are published and which are still drafts, and can pick an image by looking at it rather than by reading filenames.

**Why this priority**: These are the two highest-frequency lookup tasks in day-to-day content work. Both are currently impossible without opening records one at a time. The media problem compounds sharply as the photo library grows.

**Independent Test**: Load each list view and assert publish state is present as a column wherever drafts are enabled; load the media list and picker and assert every image record renders a visual preview.

**Acceptance Scenarios**:

1. **Given** a content list for any record type that supports drafts, **When** the editor views it, **Then** publish state is visible as a column without changing column settings.
2. **Given** the media library, **When** the editor views the list, **Then** each image record shows a thumbnail of the image itself.
3. **Given** an editor choosing an image from within a page block, **When** the media picker opens, **Then** the same visual previews are present.
4. **Given** a collapsed repeating group of images (for example a row of client logos), **When** the editor views the collapsed rows, **Then** each row is distinguishable without expanding it.
5. **Given** a non-image upload such as a PDF, **When** it appears in a list, **Then** it renders a sensible type indicator rather than a broken preview.

---

### User Story 4 - Forms read like English, not like a schema (Priority: P2)

An editor reads a form and understands what each field is for and how it will affect the page, without asking a developer and without prior knowledge of the data model.

**Why this priority**: This is the bulk of the "confusing, lots of blank fields" impression. Much of the perceived emptiness is fields belonging to variants the editor didn't choose, shown unconditionally.

**Independent Test**: Enumerate every field label and assert none is a raw camel-cased field name. Assert every field whose purpose or effect is non-obvious carries help text. Select each variant of a multi-variant block and assert only the fields relevant to that variant are shown.

**Acceptance Scenarios**:

1. **Given** an editor viewing any form, **When** they read the labels, **Then** they see plain-language names rather than mechanically title-cased field names (for example, no bare "Cta", "Seo", "Og Image", "Url").
2. **Given** a field whose purpose or effect on the rendered page is not self-evident from its label, **When** the editor views it, **Then** help text explains what it does and where it appears.
3. **Given** a block offering several layout variants, **When** the editor selects one, **Then** fields belonging only to other variants are hidden rather than shown blank.
4. **Given** a page composed of many blocks, **When** the editor collapses them, **Then** each collapsed row identifies its block by its content, not a repeated generic placeholder.
5. **Given** the search-engine metadata section, **When** the editor views it, **Then** it is labelled and explained in terms of what a visitor or search result will see.

---

### User Story 5 - Creating a page doesn't require developer knowledge (Priority: P3)

An editor creates a new page by giving it a title and filling in a starting structure, without needing to understand URL conventions or face an empty canvas.

**Why this priority**: Lower frequency than editing existing content, but it is the task most likely to stall a new editor outright. The scaffolding pattern already exists for one record type and is proven; extending it is cheap.

**Independent Test**: Create a record supplying only a title and confirm it saves with a correct auto-derived URL slug. Create a new page and confirm it opens with a usable starting structure rather than an empty body.

**Acceptance Scenarios**:

1. **Given** an editor creating a record and entering only a title, **When** they save, **Then** the record saves successfully and receives a valid URL slug derived from the title.
2. **Given** an editor who wants a specific URL, **When** they enter a slug explicitly, **Then** their value is used unchanged and validated for format.
3. **Given** an editor renaming an existing record's title, **When** they save, **Then** the existing slug is not silently rewritten (existing links keep working).
4. **Given** an editor creating a new page, **When** the form opens, **Then** it presents a starting arrangement of blocks with placeholder guidance rather than an empty body.
5. **Given** an editor entering an invalid slug, **When** they save, **Then** they receive a plain-language explanation of the required format.
6. **Given** an editor whose title derives a slug already in use, **When** they save, **Then** the save is rejected with a message naming the record that already holds that URL and suggesting an available alternative.

---

### User Story 6 - The dashboard is organized by what things are for (Priority: P3)

An editor landing on the admin home sees content types grouped by purpose, with a one-line explanation of each, and can tell which ones are theirs to edit.

**Why this priority**: Real orientation value, but an editor who has been shown the panel once can work around a flat list. Lower urgency than the screens they use every day.

**Independent Test**: Load the dashboard and assert entries are grouped under named headings and each carries a description.

**Acceptance Scenarios**:

1. **Given** an editor landing on the admin home, **When** the dashboard renders, **Then** entries are grouped under named headings that distinguish editable content from supporting reference data and from administrative records.
2. **Given** an editor reading any dashboard entry, **When** they look at it, **Then** a one-line description states what it is for.
3. **Given** record types that exist only as reference targets for other records, **When** the editor views the dashboard, **Then** they are visually separated from the primary content types.

---

### Edge Cases

- **Content already stored in fields being removed.** Some records may hold values in the `hero` group or the retained legacy body columns. Removal must confirm those values are either already represented in the block layout or are genuinely unpublished, and must not destroy content that is still the only copy of something.
- **The gitignored content-drafts seed files.** The committed seeder drives real content from `docs/content-drafts/*.json`. Any field removed or renamed must be reconciled against those files, or the next seed run fails or silently writes nothing.
- **Records whose only body lives in a parked collection.** Services and Service Pillars hold block layouts that render nowhere. Parking them must not break the relationship targets that other records and blocks depend on.
- **Blocks with no meaningful visual preview.** Some blocks are structural or invisible in isolation (embeds, forms, spacing-like blocks). These still need a distinguishable picker entry.
- **An editor mid-edit when a field disappears.** A draft saved against the old shape must still open and save cleanly after the change.
- **Media that is not an image.** PDFs are permitted uploads and have no thumbnail.
- **Slug collisions.** Two records with the same title must not silently overwrite one another's URL, and must not be silently auto-suffixed into a junk URL either — the save is rejected with a named conflict and a suggested alternative (FR-024a).
- **Live preview for parked record types.** Preview wiring that points at a retired route must not surface a broken preview pane.

## Requirements _(mandatory)_

### Functional Requirements

**Removing controls that do nothing (US1)**

- **FR-001**: The system MUST NOT present any editable field, group, global, or collection in the admin whose value has no effect on rendered public output, on page metadata, or on an editorial workflow.
- **FR-002**: The legacy hero group on the Page type MUST be removed from both the admin form and the stored schema.
- **FR-003**: Site navigation and site chrome settings MUST be withdrawn from the admin, consistent with the 2026-08-21 decision that site chrome remains code-owned.
- **FR-004**: Before withdrawal, **every** site-settings value consumed by the render path MUST be relocated into the code-owned site content constants, so that public output is unchanged on every route. Audited 2026-08-21, that is seven values, not two: `tagline` and `companyName` feed page metadata (description fallback and social-share site name), and `companyName`, `tagline`, `email`, `phone`, the full `address`, and the three `socialLinks` feed the `Organization` JSON-LD in `src/lib/structured-data.ts`. The footer already hardcodes the same address in `src/lib/site-content.ts`, so this collapses an existing duplication rather than creating one.
- **FR-005**: No half-wired global may remain: a global is either fully consumed by the render path or fully withdrawn from the admin.
- **FR-005a**: The cutover step that seeds the site-settings address so the `Organization` JSON-LD emits a postal address (`INFRASTRUCTURE_RUNBOOK.md`, added in PR #105) MUST be retired in the same change, since the values become code-owned and can no longer go dormant by being left unseeded.
- **FR-006**: Record types that have no public route MUST NOT present a page-composition body or a live-preview affordance, while remaining available as relationship targets for the records and blocks that reference them.
- **FR-007**: The retained legacy body columns from the block-composition migration MUST be dropped, and no hidden read-only remnant fields may remain in the admin schema.
- **FR-008**: The system MUST provide an automated check that fails when a field is added to a collection, global, or block without a consumer on the render path, so this class of defect cannot silently return.

**Block selection (US2)**

- **FR-009**: Blocks in the block picker MUST be organized into named categories aligned with the documented block-library categories.
- **FR-010**: Every block MUST present a visual preview representative of what it renders, distinct from every other block's preview. Previews are committed WebP images under `public/block-previews/`, one per block, produced from the showcase capture harness by a committed regeneration script. They are static assets served by the app, not media-collection uploads, not environment state, and not generated during the build.
- **FR-011**: Every block MUST carry a description stating what it produces and when to choose it; blocks with similar names MUST be disambiguated explicitly in their descriptions.
- **FR-012**: Blocks insertable within rich text MUST be distinguishable in the inline insertion menu.
- **FR-013**: An automated check MUST fail when a block is added without a category, preview, and description. The preview half of the check asserts a committed file exists for every registered block and that each file is within a size budget, so it runs without a browser, a database, or a capture run.

**List views and media (US3)**

- **FR-014**: Every content list whose record type supports drafts MUST show publish state as a default column.
- **FR-015**: Every image record MUST render a visual preview in the media list view and in every media picker, resolved from the smallest derivative the record already has. No new image size is introduced and no existing media is re-processed: measured 2026-08-21 on the real photo library, the existing 640px `mobile` derivative averages 53 KB, so a 20-item picker costs ~1 MB over an edge-cached, internal-only screen — not enough saving to justify backfilling production media with a smaller size.
- **FR-016**: Non-image uploads, and any record with no usable derivative, MUST render a meaningful type indicator rather than a broken or missing preview. This is the fallback branch of the same preview resolver as FR-015.
- **FR-017**: Collapsed rows in repeating groups of media MUST be individually identifiable without expanding them.

**Form legibility (US4)**

- **FR-018**: No field label may be a mechanically title-cased field name; all labels MUST be plain-language.
- **FR-019**: Every field whose purpose or rendered effect is not self-evident from its label MUST carry help text.
- **FR-020**: Fields that apply only to a specific variant of a block MUST be shown only when that variant is selected.
- **FR-021**: Collapsed block rows MUST identify themselves by their content rather than a repeated generic placeholder.

**Record creation (US5)**

- **FR-022**: A record MUST save successfully when the editor supplies only its title, receiving a valid URL slug derived from that title.
- **FR-023**: An explicitly entered slug MUST be honoured unchanged and validated for format, with a plain-language error on invalid input.
- **FR-024**: Renaming a record's title MUST NOT rewrite an existing slug.
- **FR-024a**: When a derived or explicitly entered slug collides with an existing record of the same type, the system MUST reject the save with a plain-language message that names the conflicting record and offers an available alternative slug. It MUST NOT auto-suffix the slug, and MUST NOT overwrite or reassign the existing record's URL.
- **FR-025**: A newly created page MUST open with a starting arrangement of blocks and placeholder guidance rather than an empty body.

**Orientation (US6)**

- **FR-026**: Admin entries MUST be grouped under named headings separating primary content, supporting reference data, and administrative records.
- **FR-027**: Every admin entry MUST carry a one-line description of its purpose.

**Non-regression (all stories)**

- **FR-028**: The rendered public site MUST be visually unchanged by this feature across every public route at both mobile and desktop viewports.
- **FR-029**: The committed seeding pipeline MUST continue to load every real content file with zero unresolved references, and those files MUST be reconciled in the same change as any field removal or rename.
- **FR-030**: Existing drafts and published records saved against the previous field shape MUST open, edit, and save cleanly after the change.
- **FR-031**: Content stored only in fields being removed MUST be identified before removal and either confirmed as already represented in the block layout or preserved.

### Key Entities

- **Page**: The general block-composed content primitive. Loses its legacy hero group; gains a starting block arrangement on creation.
- **Post**: The rich-text article primitive. Gains publish-state visibility and label/help-text improvements.
- **Case Study / Workshop / Team Member / Partner**: Block-composed record types with typed metadata. Lose their retained legacy body columns; gain publish-state visibility and form legibility improvements.
- **Service / Service Pillar**: Record types with no public route, retained as relationship targets. Lose their page-composition body and preview affordance.
- **Media**: The upload library. Gains visual previews in list and picker views.
- **Navigation / Site Settings**: Globals presenting code-owned site chrome. Withdrawn from the admin entirely — schema and table included — after all seven render-path consumers (page metadata plus the `Organization` JSON-LD) are relocated into the site content constants.
- **Homepage**: The block-composed home global. Loses its retained legacy fields; gains block row identification.
- **Layout Block**: The 45 composable page sections. Each gains a category, a visual preview, and a description.
- **Industry / Location / Category / Testimonial**: Supporting reference data, reachable only as relationship targets. Grouped separately in the dashboard.

## Success Criteria _(mandatory)_

### Measurable Outcomes

SC-002, SC-004, SC-005, SC-006, SC-007, SC-008 and SC-009 are the **release gates** — each is mechanically verifiable without a human trial. SC-001 and SC-003 are **targets, not gates**: they state the outcome the feature is aiming at, but they are not measured as a condition of shipping, consistent with the walkthrough session staying out of scope.

- **SC-001** _(target, not a gate)_: A marketing editor with no prior training on the panel can create, compose, and publish a new page from a written brief in under 20 minutes without developer assistance.
- **SC-002**: Zero editable controls remain in the admin whose values have no effect on rendered output, metadata, or an editorial workflow, verified by an automated audit that runs in CI.
- **SC-003** _(target, not a gate)_: Given a described page section, an editor identifies the correct block on the first attempt in at least 9 of 10 trials, in under 30 seconds each.
- **SC-004**: Publish state is visible without opening a record for 100% of content lists whose record type supports drafts.
- **SC-005**: 100% of image records display a visual preview in both the library list and every picker, so images can be chosen by sight rather than by filename.
- **SC-006**: Every public route renders identically before and after this feature at both mobile and desktop viewports, with no visual differences.
- **SC-007**: The committed seeding pipeline loads every real content file with zero unresolved references after the change.
- **SC-008**: Every field presented in the admin either has a self-evident label or carries help text; no label is a mechanically title-cased field name.
- **SC-009**: Adding a new block or field without its required category, preview, description, or render-path consumer fails CI, so the improvements cannot decay.

## Assumptions

- **Site chrome stays code-owned.** Decided 2026-08-21: navigation structure, office address, phone, social links, and footer text remain code changes. Rationale: navigation URLs are unvalidated free text coupled to the route table and the 301 redirect map, so a bad nav edit would ship a broken link into the primary navigation, while the underlying values change roughly once a decade. Revisit if that frequency changes.
- **The editor role is the target persona.** Improvements are scoped to what a non-admin editorial user sees. Administrative surfaces (user management) need orientation grouping but not the full legibility pass.
- **The existing block library is stable.** This feature adds presentation metadata to the 45 existing blocks; it does not add, remove, or redesign blocks.
- **Block previews are committed WebP screenshots** derived from the existing showcase capture harness, which already renders every block in isolation. Measured 2026-08-21: at 480px wide, WebP q78 averages ~7.8 KB per block, so the full set of 45 is ~340 KB. Committing them keeps the picker working identically in local dev, CI, and every deployed lane, and keeps Playwright and Postgres out of the image build. Unlike the gitignored capture directories, these change only when a block's design changes.
- **Writing the editor guide and running the walkthrough session are out of scope** for this spec. Both depend on the panel settling first and are tracked separately.
- **No public-facing copy, photography, or content is authored here.** This is an admin-only change; the content track is unaffected.
- **Staging is currently torn down** (2026-08-14), so verification runs against a local mirror and CI rather than a deployed staging environment.

## Out of Scope

- Writing the editor-facing guide document.
- Running the training/walkthrough session with the marketing lead.
- Adding, removing, or redesigning layout blocks.
- Any change to public routes, templates, rendered output, or site copy.
- Wiring navigation or site settings to become CMS-editable.
- Role or permission model changes beyond what orientation grouping requires.
